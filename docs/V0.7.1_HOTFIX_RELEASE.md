# CtrlSpeak v0.7.1 — recording safety and Midnight Signal fidelity

Status: released and deployed on 2026-08-18. The installed Windows copy was not
changed automatically; user-operated microphone, visual/DPI, and updater
acceptance remain pending under the boundary in section 7.

Target branch: `v0.7`

Target tag: `v0.7.1`

Maintained build specification: `packaging/CtrlSpeak_v0.7.spec`

This patch preserves the v0.7.0 Midnight Signal product and API contract while
correcting one release-blocking Windows recording crash and visual differences
between the packaged interface and the approved design direction. The v0.7.0
baseline remains documented in `V0.7_MIDNIGHT_SIGNAL_RELEASE.md`.

## 1. Confirmed v0.7.0 incident

Pressing right Ctrl in the packaged Windows application could terminate the
entire process before recording became usable. Two independent Windows Error
Reporting records identified the same failure:

- faulting module: `_portaudio.cp312-win_amd64.pyd`;
- exception: `0xc0000005` native access violation; and
- identical fault offset and WER signature on both reproductions.

The Python log ended without a traceback because the access violation occurred
inside the native extension. The packaged PyAudio module matched the clean
build environment, so the failure was not a missing PyInstaller import or
asset.

The v0.7.0 recording-start path launched microphone capture and then launched a
UI cue on another thread. Each path independently created and terminated a
PyAudio manager. They could therefore enter PortAudio's process-global Windows
host initialization at the same time. Cancellation could produce a related
overlap by playing feedback while the recorder was still exiting.

## 2. Audio-lifecycle hotfix contract

v0.7.1 must satisfy all of these conditions:

- microphone capture and UI feedback never create competing PortAudio
  initialization or termination lifecycles;
- recording-start feedback cannot terminate, reinitialize, or otherwise alter
  a live capture runtime;
- cancellation feedback waits for, or uses a backend independent from, a
  recorder that is still flushing;
- an unavailable cue/output backend does not stop microphone capture;
- no attempt is made to recover from a native access violation after it occurs;
  the invalid concurrency must be prevented instead;
- busy state remains true until the actual recorder exits, and stale session
  workers cannot clear a newer recording or transcription;
- Quit and updater shutdown signal active work, join for a bounded interval,
  attempt exact-path WAV cleanup, and leave startup able to remove a bounded
  stale recording that was locked beyond that interval; and
- audio cues remain finite, respect saved mute/volume settings, do not change
  pitch, and retain no captured speech or transcript data.

Using a Windows-native WAV playback backend for UI feedback is compatible with
this contract because it leaves PyAudio capture-only. A different
implementation is acceptable only if its process-wide lifetime coordination
covers initialization, every live stream, and termination; serializing only
the constructor is insufficient.

## 3. Midnight Signal visual-fidelity corrections

The hotfix must bring the real control center, tray flyout, recording capsule,
processing overlay, and terminal states back into alignment with the approved
Midnight Signal direction:

- clean graphite surfaces with restrained cyan/green status accents;
- clear typography, spacing, surface hierarchy, and compact information
  density rather than a generic form layout;
- a slim recording capsule and elongated processing treatment, never providers
  arranged in a circle around a microphone;
- provider, route, dBFS, duration, and latency detail only when derived from
  live measured state;
- no invented sample measurements, inferred provider winner, or client time
  relabelled as server inference;
- readable non-colour state labels, visible keyboard focus, reduced-motion
  behaviour, and usable layouts at 100%, 125%, 150%, and 200% Windows scaling;
- overlays stay on the active monitor, do not steal focus, and cannot be closed
  by a stale dismissal timer from an earlier session; and
- no transcript text, audio content, API key, bearer token, correction phrase,
  or clipboard content enters UI snapshots or diagnostics.

These are corrective presentation changes. They do not authorize fake
telemetry, a new circular provider selector, transcript history, or a change to
the established recording/transcription workflow.

## 4. Compatibility and deployment boundary

The `/health`, `/v1/capabilities`, `/v1/transcribe`, correction, and feedback
contracts remain backward-compatible. The desktop, server package, and server
runtime versions are synchronized at 0.7.1 so the release tooling and deployed
role health remain unambiguous, but the crash fix itself is desktop-only.

The dedicated OpenStack `CtrlSpeak` host remains the gateway. The Ubuntu GPU
machine remains the worker. Nova remains the WireGuard/Hermes host and must not
gain a CtrlSpeak gateway or inference listener. Hermes needs no adapter or
configuration change when the existing authenticated gateway URL and API
contract remain unchanged.

No release step may overwrite protected environment files, service tokens,
credential vault entries, correction/audit databases, model caches, user
settings, or host-specific Hermes code.

## 6. Required automated gates

Run from a clean supported environment:

```text
python -m pytest -m core_headless
python -m pytest -q tests/core
python -m pytest -q server/whisper_transcription/tests
python -m compileall main.py utils scripts tests server/whisper_transcription/app
python scripts/release.py check-version --tag v0.7.1
git diff --check
```

The deterministic regression must hold capture open while recording-start and
cancellation feedback are requested. It must fail if a second PortAudio owner
initializes or terminates while that capture is live. Lifecycle tests must also
cover cancel/release races, session generations, bounded shutdown, and exact
temporary-file cleanup.

Release CI must build on clean Windows and Linux Python 3.12 runners, execute
the packaged health receipt, and verify the Windows PE file/product versions
against the tag before signing any manifest.

## 7. Required physical and frozen-artifact gates

Headless tests do not prove this hotfix. Before publishing:

1. Use a physical Windows microphone and cues enabled for at least 50
   right-Ctrl press/release cycles, including fast presses and cancellations.
2. Repeat against the exact one-file release candidate, not only source mode.
3. Confirm recording, release, cancellation, next-session start, and Quit stay
   responsive and leave no unexpected WAV.
4. Inspect the matching Windows Application event-log interval. There must be
   no Application Error or WER crash for CtrlSpeak, `_portaudio`, or exception
   `0xc0000005`.
5. Repeat with cues muted and with output playback unavailable; capture must
   still work.
6. Exercise control center, tray flyout, all overlay phases, keyboard focus,
   reduced motion, and active-monitor placement at supported scaling factors.
7. Update an installed v0.7.0 copy through **Check for updates** to the signed
   v0.7.1 candidate. Confirm the stable executable path and user configuration
   survive. Do not use v0.7.0 for recording during this updater-only check.

The complete platform checklist remains in `TESTING.md`.

### Operator boundary for this recovery

For this incident, the user explicitly stopped Computer Use and prohibited the
agent from operating the desktop UI or microphone. The agent must not bypass
that boundary merely to complete an interactive acceptance item. The signed
hotfix may therefore be published after every automatable gate, exact frozen
metadata check, Linux staging test, and deterministic native-audio lifecycle
regression passes, provided the release record says plainly that the physical
microphone, visual/DPI, and installed-updater checks remain user-operated and
have not been claimed as passed. The installed application must not be replaced
automatically.

## 8. Release, deployment, and rollback acceptance

Only after all automatable gates pass and any user-operated gates are recorded
truthfully under the boundary above:

1. Commit and push the reviewed `v0.7` branch.
2. Create and push the immutable annotated `v0.7.1` tag.
3. Let the release workflow build, test, sign, audit the draft, and publish
   exactly five public assets.
4. Independently download those assets and run
   `python scripts/release.py verify --directory <dir> --tag v0.7.1`.
5. Back up and update the dedicated gateway/worker source one role at a time if
   version-matched service deployment is in scope. Preserve state and verify
   authenticated health, role, correction inventory, telemetry, and a real
   restricted-language transcription.
6. Install the signed Windows candidate only after its native-audio stress
   check passes.

Rollback uses the existing updater health receipt and external replacement
helper for the desktop. Server rollback restores timestamped source together
with its matching state/database snapshot. If a physical audio gate is run
before publication and fails, v0.7.1 must not be published. If that gate is
user-operated after publication under the boundary above, any failure requires
immediate rollback or a newer immutable hotfix; never move the tag or replace
assets after users could have consumed them.
