# CtrlSpeak 0.8.2 — differential executable updates

## Purpose and rollout

Keep one `CtrlSpeak.exe` and the existing signed updater, but download only a
verified binary delta when it is economical. This release installs the decoder
and the new client logic. An existing 0.8.1 updater still downloads the complete
0.8.2 executable; it cannot acquire a decoder before that decoder is installed.

**0.8.3 is the planned end-user trial:** install 0.8.2 first, then use Check for
updates to install 0.8.3. Its proposed UI feature is an animated keyboard/mode
instruction guide. Do not implement/publish 0.8.3 merely to claim this trial is
already done; it remains separate work and later user acceptance.

Development branch: `codex/differential-updates-v0.8.2`. Current release/tag/assets
are not overwritten. Windows installation remains a user action. Gateway,
Ubuntu worker and Nova external helper use the coordinated release transaction;
no Hermes core/environment patch or Hermes restart is required.

larger patch, and there is no promise that every update is a few hundred KB.

## Signed format and selection

The canonical Ed25519-signed manifest keeps `schema_version: 1` and the existing
two full artifacts in `assets`. An additive `deltas` list describes patches.
Older updaters ignore that list and can still install the full executable.

Each supported entry binds:

- Algorithm `xdelta3-vcdiff-1`, target platform/architecture/standard variant.
- Base version, exact base size and SHA-256; version text alone is insufficient.
- Target full size and SHA-256, matching the signed full artifact.
- Patch filename, release-bound HTTPS URL, byte size and SHA-256.
- Minimum patch-aware updater version 0.8.2.

Known-algorithm entries are validated and duplicate base versions rejected.
Unknown future algorithms are not selected; full updates remain available.
Current limits are 12 manifest entries, 128 MiB per patch and at most 80% of
the full artifact's size. Patches outside the resource/savings budget are not
published as usable deltas. Runtime accepts no unsigned tool or arbitrary URL.

## Update transaction

1. Check GitHub and verify the canonical manifest signature as before.
2. On the background updater thread, find an exact installed base and select
   the corresponding supported patch. Show its method and actual transfer size.
3. Check conservative temporary free-space requirements. Network savings do
   not remove full-file reconstruction, sibling, backup or one-file extraction.
4. Download/resume the signed patch into a separate transaction-owned file.
5. Recheck base identity and reconstruct a **separate candidate**, with bounded
   native runtime/output and cancellation. Never edit the installed executable.
6. Verify the reconstructed full size and SHA-256 against the signed full asset.
7. Use the existing detached-helper, atomic replacement, post-update health
   confirmation and startup-failure rollback. Revalidate the signed target for
   differential handoff/application; never treat a `.vcdiff` as an executable.

On corrupt/unavailable patches or reconstruction/base mismatch, use at most one
full-download fallback, explicitly announced in the UI. Bad main signatures,
user cancellation and insufficient disk space do not trigger that fallback.
Both the fallback and ordinary full download retain exact signed hash checking.

One owned download/patch worker may run at a time. A cancelled worker must finish
closing before another operation starts. Native tooling runs without a shell,
without a visible console, with external compression helpers disabled, pinned
tool bytes, a 64 MiB source window and an eight MiB encoding window. Its default
apply deadline is 120 s and encoding deadline 180 s. Kill/reap occurs before
fallback/retry. A target-size guard limits native output on the staged path.

## Native tool provenance and packaging

Xdelta **3.2.2**, unmodified official Windows/Linux x86-64 binaries, Apache-2.0.
`scripts/fetch_patch_tool.py` is build-time-only. It verifies hardcoded archive,
extracted binary and license hashes from `utils/delta_tools.py`. The license and
third-party notice are bundled. No decoder is downloaded by an installed app.

The tool is bundled as data so PyInstaller does not rewrite its ELF/RPATH bytes.
Linux owner-execute permission is restored only after the pinned hash passes.
Both packaged health checks perform a real, small native roundtrip in temporary
files. They do not launch a desktop GUI or dictate into an application.

Upstream references: [release](https://github.com/jmacd/xdelta/releases/tag/v3.2.2),
[source/license](https://github.com/jmacd/xdelta/tree/v3.2.2/xdelta3).

## CI/release changes

- Build the usual full Windows/Linux artifacts and native health-check them.
- Fetch up to three recent stable **patch-aware** bases (0.8.2 onward), verify
  their manifests and binaries, generate direct base-to-target patches, and
  reconstruct/hash-check each. Skipped releases do not require a patch chain.
- For the initial 0.8.2 release only, use 0.8.1 as the production-pipeline base
  to prove patch generation, though its installed updater cannot consume it.
- Sign patch metadata together with the full assets. `SHA256SUMS` covers every
  declared patch, and the independent uploaded-release audit checks the exact
  signed asset set. The former fixed five-asset count becomes five plus patches.
- Keep machine-readable delta generation/roundtrip evidence as a CI artifact.
- Stage/verify the mandatory backend fleet before publishing the desktop update,
  preserving gateway corrections and existing backend rollback selectors.

Full executables remain downloadable for new installs, unsupported bases,
modified executables and recovery. Explicit signed rollback to 0.7.7 remains.

## Storage, receipts and 0.8.3 acceptance

The Updates page reports patch versus full transfer, reconstructing/verification
state and network byte progress. A redacted installed-update receipt survives
restart and is included in Copy diagnostics: version, method, download bytes and
full executable bytes. This is the evidence to inspect after 0.8.3 installs.

After a new helper confirms startup health, it may prune only known payload
filenames in older **successfully completed** transaction folders. Keep at least
the newest two completed installs plus the latest explicit 0.7.7 rollback.
Retain metadata/audit logs and all active, failed, unknown or linked entries.
No recursive deletion, settings/models/keys/corrections removal or personal-file
cleanup is part of this policy. Recovery states can still consume space and
must be inspected separately rather than automatically removed.
