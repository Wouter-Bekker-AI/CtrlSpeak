# CtrlSpeak v0.5 self-update and release plan

Status: approved and being implemented on branch `v0.5`
Baseline: corrected `v0.4` branch (`APP_VERSION = "0.4.0"`)
Target: `v0.5` branch and first release `v0.5.0`
Last updated: 2026-08-14

## 1. Goal

CtrlSpeak v0.5 will add a safe in-application update experience for the standard
Windows and Linux builds. A user will be able to open the CtrlSpeak control
center, select **Check for updates**, review an available release, and choose to
download and install it. CtrlSpeak will close, apply the update with an external
helper process, relaunch, and automatically restore the previous executable if
the new version does not pass its startup health check.

The desired operator workflow is:

1. Make and review source changes in Git.
2. Update the application version and create a signed version tag.
3. Push the tag to GitHub.
4. GitHub Actions tests the tagged source, builds the Windows and Linux
   executables, creates checksums and a signed update manifest, and publishes a
   GitHub Release.
5. Installed copies of CtrlSpeak discover that release through the GitHub API.
6. The user approves the update and CtrlSpeak installs the correct artifact for
   the current operating system and architecture.

This removes the need for a developer to build, copy, or distribute each new
executable manually. A new executable is still produced for every release, as
Python source embedded in a PyInstaller executable cannot be safely patched in
place. The important change is that release automation builds it and the
installed application retrieves it.

## 2. Reference implementations reviewed

### 2.1 Storm competitor-analysis updater

The design is informed by the updater in:

`C:\Users\woute\personal_projects\Storm_comp_analysis_update_test\source_repo`

Storm currently does the following:

- queries the latest GitHub Release and falls back to tags;
- compares the published version with its embedded application version;
- identifies a downloadable `.exe` release asset;
- downloads a replacement executable through an external PowerShell process;
- waits for the running application to exit;
- renames the old executable to `.bak`;
- moves the new executable into place and relaunches it; and
- uses a tag-triggered GitHub Actions workflow to build and publish the release
  executable.

CtrlSpeak will retain the useful product experience but strengthen the design:

- exact product/platform/architecture asset matching instead of choosing any
  filename containing `.exe`;
- no tag-only fallback for installable updates, because a tag without a verified
  binary is not an update;
- streaming downloads with visible progress rather than a silent full-file
  operation;
- strict version parsing;
- release-manifest signature, SHA-256, and file-size verification;
- an atomic same-directory executable replacement;
- explicit startup health confirmation and automatic rollback;
- native Windows and Linux paths;
- application-data logs and transaction state rather than helper files written
  beside arbitrary user documents; and
- clear separation between packaged installations and source checkouts.

### 2.2 Handy speech-to-text application

The plan was also revisited after a source-level review of the MIT-licensed
Handy project at:

`https://github.com/cjpais/Handy`

The review used main commit
`549cbde3ebb72459f7f7230783931a45222018a1` and the published `v0.9.5`
release. Handy is a Tauri/React/Rust application rather than a Python/Tk
application, so CtrlSpeak will not copy its updater implementation directly.
The following design patterns are nevertheless applicable:

- exact signed platform/architecture entries whose URLs point at immutable
  tag-specific GitHub Release assets;
- explicit checking, downloading, verifying, installing, and up-to-date UI
  states;
- an operation coordinator and generation IDs so late worker callbacks cannot
  mutate the state of a newer operation;
- resumable partial downloads with strict HTTP Range validation, finite stall
  timeouts, size caps, checksum verification, and atomic finalization;
- settings schema migrations that salvage valid fields instead of resetting an
  entire settings file because one value is malformed;
- a one-time **What's new** view after a successful update;
- clean separation between installed, portable-like, and source-checkout
  behavior; and
- release workflows that build a draft release, audit the actual packages, and
  publish only when the whole platform matrix succeeds.

CtrlSpeak deliberately keeps stronger requirements than Handy in several
areas: the update helper retains a verified backup, requires a post-update
health receipt, and rolls back automatically. Handy's fuzzy custom-word
replacement, free-form LLM transcript polishing, transcript-content logging,
and lack of application-level updater rollback are not adopted by this plan.

## 3. Scope

### 3.1 Included in v0.5

- A manual **Check for updates** action in the management window.
- Stable-channel GitHub Release discovery.
- Windows x86-64 packaged updates.
- Linux x86-64 packaged updates.
- Background release checks and downloads that do not freeze Tk, the tray,
  recording, or the local server.
- Release notes and a link to the GitHub Release.
- A one-time **What's new** summary after a successful update, with an opt-out.
- Explicit user confirmation before download/install.
- Resumable download progress, verification progress/state, cancellation, and
  actionable user-visible error messages.
- Signed manifest and artifact verification.
- External apply-update mode.
- Atomic replacement, backup, health handshake, and rollback.
- Process-wide update coordination with stale-callback protection.
- Settings schema migration, backup, and per-field recovery.
- Update transaction logs and stale-download cleanup.
- Automated test, build, manifest, and release workflows.
- Documentation for maintainers and end users.

### 3.2 Deliberately deferred

- Silent or forced updates.
- Mandatory background checks on every startup.
- Delta/binary-diff updates. CtrlSpeak v0.5 downloads the complete packaged
  executable.
- Updating a source checkout by running `git pull` from the GUI.
- Native Wayland hotkeys or injection; the v0.4 X11 boundary remains unchanged.
- Automatic installation of Linux system packages or NVIDIA drivers.
- Microsoft Store, MSIX, apt, rpm, Flatpak, or AppImage distribution.
- A separate Watcher auto-update channel, unless it is explicitly designed and
  given its own product identity before release.
- Automatic privilege elevation for an unwritable installation directory.
- Prerelease/beta channels. The initial updater consumes stable releases only.

## 4. Release and branch model

### 4.1 Baseline preparation

Before creating v0.5:

1. Keep the cross-platform test correction in
   `tests/core/test_config_paths.py`. The test must patch `Path.home()` directly
   so it behaves consistently when Linux semantics are simulated on Windows.
2. Run the complete v0.4 core suite on Windows; the current verified result is
   `77 passed`.
3. Commit that correction to `v0.4` as a narrowly scoped fix.
4. Push `v0.4` so the cloud release baseline and local baseline agree.
5. Create local and remote branch `v0.5` from the corrected `v0.4` tip.

The existing untracked Watcher video, camera sound, and semantic-audit document
must not be added, removed, or folded into v0.5 unless a separate decision puts
them in scope.

### 4.2 Version source of truth

- Set the single `APP_VERSION` source in `utils/version.py` to `0.5.0` on the new branch.
- Use strict semantic release tags of the form `vMAJOR.MINOR.PATCH`, initially
  `v0.5.0`.
- The release workflow must fail if the tag without its leading `v` does not
  equal `APP_VERSION`.
- The manifest version, executable runtime version, Git tag, and GitHub Release
  version must all match.
- Stable releases are immutable. Never move an existing release tag or replace
  an asset after clients may have consumed it. Publish a new patch release.

### 4.3 Branch use

- `v0.5` is the release-development branch for this work.
- Release tags are created from reviewed commits on `v0.5`.
- The existing historical `main`, `dev`, BOT, and prior version branches are not
  rewritten as part of this project.
- Moving the GitHub default branch to `v0.5` or merging the completed release
  line into a new primary branch is a separate repository-governance decision.

## 5. Product identity and artifact naming

The updater must never select an artifact by loose substring matching.

### 5.1 Trusted product identity

Hard-code the following trust identity in the packaged standard application:

- GitHub owner: `Wouter-Bekker-AI`
- GitHub repository: `CtrlSpeak`
- product identifier: `ctrlspeak`
- update channel: `stable`

These values are application trust roots, not ordinary editable settings. A
future private mirror or enterprise channel should use a separately built and
identified client rather than allowing a settings file to redirect updates to
an arbitrary repository.

### 5.2 Release assets

Use stable, unambiguous release asset names:

- `CtrlSpeak-windows-x86_64.exe`
- `CtrlSpeak-linux-x86_64`
- `update-manifest.json`
- `update-manifest.sig`
- `SHA256SUMS`

The installed filename is stable across releases:

- Windows: `CtrlSpeak.exe`
- Linux: `CtrlSpeak`

The downloaded release filename may include the platform but is installed over
the stable local filename. A file called `CtrlSpeak_v0.4.exe` that silently
becomes v0.5 is confusing, so v0.5.0 is the one-time migration to a stable name.

### 5.3 Variant isolation

- Standard CtrlSpeak accepts only manifest entries with product
  `ctrlspeak`.
- A future Watcher updater must use a distinct product identifier, signing
  policy, artifact name, and preferably a distinct release channel.
- A standard build must reject Watcher and client-only assets even if their
  platform and version otherwise match.
- If client-only packaging returns later, add an explicit `variant` field and
  exact matching tests before publishing it.

## 6. Signed update manifest

Every installable release must contain a machine-readable manifest. Proposed
schema:

```json
{
  "schema_version": 1,
  "product": "ctrlspeak",
  "channel": "stable",
  "version": "0.5.1",
  "tag": "v0.5.1",
  "published_at": "2026-08-14T12:00:00Z",
  "release_url": "https://github.com/Wouter-Bekker-AI/CtrlSpeak/releases/tag/v0.5.1",
  "minimum_updater_version": "0.5.0",
  "assets": [
    {
      "platform": "windows",
      "architecture": "x86_64",
      "variant": "standard",
      "name": "CtrlSpeak-windows-x86_64.exe",
      "url": "https://github.com/Wouter-Bekker-AI/CtrlSpeak/releases/download/v0.5.1/CtrlSpeak-windows-x86_64.exe",
      "size": 219711698,
      "sha256": "<64 lowercase hexadecimal characters>"
    },
    {
      "platform": "linux",
      "architecture": "x86_64",
      "variant": "standard",
      "name": "CtrlSpeak-linux-x86_64",
      "url": "https://github.com/Wouter-Bekker-AI/CtrlSpeak/releases/download/v0.5.1/CtrlSpeak-linux-x86_64",
      "size": 210000000,
      "sha256": "<64 lowercase hexadecimal characters>"
    }
  ]
}
```

Requirements:

- Serialize the manifest in a defined canonical byte form before signing.
- Sign those exact bytes with a dedicated Ed25519 release key.
- Store only the public verification key in the CtrlSpeak executable.
- Store the private signing key in a protected GitHub Actions secret or perform
  the signing in a separately protected release job.
- Reject an absent signature, invalid signature, unsupported schema, wrong
  product/channel/variant, invalid semantic version, duplicate matching asset,
  unexpected architecture, missing checksum, mismatched size, or mismatched
  hash.
- Require each signed asset URL to use HTTPS and the hard-coded trusted GitHub
  owner/repository, exact signed tag, and exact asset name. Do not accept a
  redirect or manifest URL that changes product identity or release tag.
- Consume the immutable signed asset URL instead of reconstructing a download
  URL from a filename convention. Asset naming may evolve later without making
  old updater logic guess.
- HTTPS transport is required but is not treated as artifact integrity by
  itself.
- If signing-key rotation is ever needed, release a client containing both the
  old and new public keys while releases are still signed by the old key, then
  rotate in a later version.

Authenticode signing for Windows should also be added when a suitable code-
signing certificate is available, but Authenticode is complementary to the
cross-platform signed manifest and not a replacement for it.

## 7. Update discovery

Create `utils/update_manager.py` with pure, testable components for:

- strict semantic-version parsing and comparison;
- current platform and architecture normalization;
- GitHub Release API calls;
- manifest and signature retrieval;
- manifest parsing and verification;
- exact artifact selection;
- release-status representation;
- resumable, bounded artifact download;
- size and SHA-256 verification;
- transaction staging; and
- readable error classification.

Create a small process-wide `UpdateCoordinator` around those pure components.
It owns the single active update operation, current state, cancellation token,
and monotonically increasing generation ID. Every worker event carries its
generation; the UI and coordinator ignore results from cancelled or superseded
generations. This prevents a slow first check, delayed hash task, or late
download callback from overwriting the state of a newer operation.

### 7.1 GitHub behavior

- Query `https://api.github.com/repos/Wouter-Bekker-AI/CtrlSpeak/releases/latest`.
- Send a CtrlSpeak-specific `User-Agent`, GitHub JSON `Accept` header, and finite
  connect/read timeouts.
- Stable mode ignores drafts and prereleases. GitHub's `releases/latest`
  behavior supports this, but response fields must still be validated.
- Do not fall back to the latest tag. A tag can exist without tested binaries,
  a manifest, or a signature.
- Treat API rate limits, offline state, TLS failures, invalid JSON, missing
  assets, and an invalid manifest as distinct user-facing states.
- Do not log access tokens, API backend credentials, signed URLs containing
  secrets, or complete response headers.

### 7.2 Version behavior

- `latest == current`: report **CtrlSpeak is up to date**.
- `latest < current`: report that this build is newer than the latest stable
  release; do not offer a downgrade.
- `latest > current`: offer the verified compatible update.
- Reject malformed versions instead of guessing.
- Enforce `minimum_updater_version`. If the existing updater is too old, show a
  manual-download requirement instead of attempting an unsafe transaction.

## 8. Management-window interface

Add an **Application updates** card near the top of `ManagementWindow`, after
the system-status card and before backend/device controls.

The card contains:

- current version: `CtrlSpeak 0.5.0`;
- channel: `Stable`;
- last checked timestamp, or `Never`;
- status text;
- **Check for updates** button;
- a release link or **View release notes** action when a release is known;
- **Download and install** when a verified newer release exists; and
- a determinate progress bar and byte/percentage text during download.

### 8.1 UI state machine

Use explicit states:

1. `idle`
2. `checking`
3. `up_to_date`
4. `available`
5. `downloading`
6. `verifying`
7. `ready_to_install`
8. `launching_updater`
9. `awaiting_health_confirmation`
10. `installed`
11. `rolled_back`
12. `failed`
13. `manual_install_required`

Only valid actions are enabled in each state. Repeated clicks must not start
multiple checks, downloads, or updater processes. `installed` and `rolled_back`
are reconstructed from the verified transaction journal on the next healthy
startup, rather than relying on in-memory UI state from the process that exited.

### 8.2 Threading

- Network and hashing work runs on a worker thread.
- Tk widgets are updated only through the existing management UI queue.
- Worker callbacks are accepted only when their generation ID still matches the
  active coordinator generation.
- Closing the management window does not corrupt an active download; the
  operation either continues with tray notification or is cleanly cancelled at
  a defined boundary.
- The Ctrl+Right-Control listener, audio capture, API calls, and local server
  remain responsive during update checks and downloads.
- Applying the update is blocked while a recording or transcription is active,
  or the user is asked to wait/cancel that operation safely.
- The same busy-state interface must be extensible to the future semantic audit
  and correction-verification barrier without making that separate feature part
  of the v0.5 updater scope.

### 8.3 Errors and recovery actions

Network, manifest, verification, disk, permission, helper-launch, health, and
rollback failures must appear in the management window or a tray-accessible
message. Do not leave an updater failure only in a console or log file. Each
message contains a stable error category, concise explanation, safe next step,
and **Copy diagnostics** action that copies only redacted update metadata.

Retry starts a new generation. It may reuse a compatible verified partial as
defined in section 9, but it never reuses an unverified in-memory decision.

### 8.4 User confirmation

Before download/install, show:

- current and target versions;
- release title/summary;
- approximate download size;
- platform artifact selected;
- notice that CtrlSpeak will close and reopen; and
- notice that settings and downloaded models will be retained.

The default button is **Cancel**, not **Install**.

## 9. Download and staging

All persistent update state lives under the platform CtrlSpeak data directory:

- Windows: `%APPDATA%\CtrlSpeak\updates`
- Linux: the appropriate XDG CtrlSpeak data/config location used by the v0.5
  storage decision

Each attempt receives a random transaction ID and directory containing:

- canonical manifest bytes;
- signature;
- release metadata;
- `.partial` download;
- verified candidate;
- transaction journal;
- health request/response markers; and
- updater log.

Rules:

- Stream the response in bounded chunks.
- Impose a maximum size derived from the signed manifest plus a small fixed
  tolerance; never accept an unbounded download.
- Show progress from `Content-Length` when available, but trust the signed
  manifest size for final validation.
- Use finite connect, response-header, and per-chunk stall timeouts. A server
  that stops sending bytes cannot leave the updater stuck indefinitely.
- Throttle progress events to a bounded rate so Tk is not flooded with worker
  callbacks.
- Support clean cancellation during download. A compatible partial may be kept
  for resume, but it is never executable and is never renamed to the verified
  candidate before all checks pass.
- Bind a partial to the exact product, version, asset name, signed URL, expected
  size, SHA-256, and manifest hash in the transaction journal. A partial from a
  different release or manifest is stale and cannot be resumed.
- If a partial is larger than the signed size, delete it. If it already equals
  the signed size, hash it before making any network request and accept it only
  on an exact match.
- Resume with `Range: bytes=<partial-size>-`. Accept `206 Partial Content` only
  when `Content-Range` begins at exactly that offset. If the server returns
  `200 OK` to a range request, truncate and restart rather than appending a
  complete file to the partial.
- Treat `416 Range Not Satisfiable` as success only when the existing partial
  has the exact signed size and SHA-256. Otherwise clear it and restart/fail
  safely.
- Abort and remove the tainted partial immediately if the server advertises or
  sends more than the signed maximum. Verify final on-disk length even when
  `Content-Length` is missing or false.
- Flush and fsync the completed partial before hashing and atomically rename it
  to the transaction's verified-candidate filename only after size and SHA-256
  succeed.
- Verify signature, product metadata, size, and SHA-256 before asking the main
  application to exit.
- Copy the verified candidate to a sibling `.new` file in the installation
  directory and verify it again. This ensures the final replacement is on the
  same filesystem and can be atomic.
- On Linux set and verify the executable permission before replacement.
- Probe write access in the installation directory early. If it is not
  writable, keep the current application running and provide manual-install
  guidance; do not request elevation silently.

## 10. External update application

The running application cannot safely replace its own executable. Add internal
command-line modes that are not shown as normal user options:

- `--apply-update <transaction-file>`
- `--post-update <transaction-id>`

The normal packaged application copies itself to the transaction directory and
launches that copy in apply-update mode. Because the helper runs from a separate
path, it remains available while the installed executable is replaced. Source
mode must not use this path.

### 10.1 Graceful handoff

When the verified update is ready:

1. Ensure no other update transaction is active.
2. Write and fsync the transaction journal.
3. Start the detached copied updater.
4. Ask the user to confirm the final restart.
5. Stop recording/hotkey listeners.
6. Stop the discovery listener and HTTP server.
7. Stop processing audio feedback.
8. Close the management UI and tray.
9. Release the single-instance lock.
10. Exit normally so `atexit` cleanup runs.

Avoid `os._exit` for updates unless a bounded graceful shutdown has failed and
the transaction log records that fallback.

### 10.2 Atomic Windows/Linux replacement

The updater process:

1. waits for the original PID and PyInstaller bootloader process to exit;
2. retries file access for a bounded period because one-file bootloaders and
   antivirus software may briefly retain handles;
3. copies the original executable to a verified `.previous` backup without
   removing the original;
4. verifies the backup hash and candidate hash;
5. places the verified `.new` candidate beside the installed executable;
6. uses a same-directory atomic replace (`os.replace` or the platform-specific
   equivalent) so there is no intentional interval with no installed file;
7. launches the new executable with `--post-update <transaction-id>`; and
8. watches for health confirmation.

The backup remains intact until health confirmation. The updater never deletes
the user's models, CUDA cache, logs, settings, API token, corrections database,
or recordings unrelated to its transaction.

### 10.3 Health confirmation

The new process writes a success marker only after it has:

- acquired the single-instance lock;
- loaded and validated settings;
- completed any settings-schema migration;
- activated the selected transcription-backend configuration;
- created the management UI root;
- initialized the platform adapter sufficiently to report an actionable state;
- reached the point where tray mode or the management-only fallback can run;
  and
- opened logging successfully.

The updater also verifies that the new process remains alive for a short grace
period after writing the marker. A marker contains the transaction ID, running
version, executable path, PID, and timestamp so a stale marker cannot approve a
different transaction.

### 10.4 Rollback

Rollback occurs if:

- the new executable cannot be launched;
- it exits before health confirmation;
- it reports a startup failure;
- the health deadline expires; or
- its reported version/path/transaction does not match.

Rollback procedure:

1. terminate the failed new process if it is still running;
2. atomically restore the verified `.previous` backup;
3. relaunch the previous executable with a `--rollback-notice` transaction ID;
4. retain logs, manifest, and failure metadata for diagnosis; and
5. show a concise message that the old version was restored.

After successful health confirmation, retain at most one previous executable
for a short cleanup window, then remove it on a later healthy startup. Cleanup
must never delete a file outside the exact updater-owned paths.

## 11. Source-checkout behavior

Classify the runtime once at startup as one of:

- `source_checkout` (`sys.frozen` is false);
- `packaged_user_writable`; or
- `packaged_manual_install_required` because the executable/install directory
  is not safely writable.

The classification is included in updater diagnostics and drives available UI
actions. Runtime state remains in CtrlSpeak's application-data directories; a
copied packaged executable must not start writing settings or update journals
beside itself merely because it is portable-like.

When `sys.frozen` is false:

- **Check for updates** may report the latest published release for developer
  awareness.
- **Download and install** is disabled.
- The UI explains that a source checkout is updated through Git and refers to
  the current branch/status.
- CtrlSpeak must not run `git fetch`, `git checkout`, `git pull`, dependency
  installation, or PyInstaller automatically from the GUI.

This prevents local changes from being overwritten and avoids turning an
installed desktop updater into a general remote-code execution path.

## 12. GitHub Actions automation

Add two workflows.

### 12.1 Continuous integration

`.github/workflows/test.yml` runs on pushes and pull requests affecting v0.5:

- Windows and Linux supported Python versions;
- core headless tests;
- updater tests;
- compile/import checks;
- `git diff --check` equivalent hygiene;
- manifest schema tests; and
- static validation of Windows/Linux PyInstaller specs.

Physical microphone, tray, X11 injection, CUDA performance, and real packaged
self-update tests remain release-host/manual checks where CI cannot reproduce
the desktop environment.

### 12.2 Tagged release

`.github/workflows/release.yml` runs only for strict tags such as `v0.5.0`:

1. Check out the exact tag commit.
2. Verify tag/version equality and clean repository state.
3. Run the test suite on Windows and Linux.
4. Build Windows x86-64 on a Windows runner.
5. Build Linux x86-64 on the oldest supported Ubuntu/glibc runner.
6. Perform packaged `--version`/`--health-check` smoke tests.
7. Upload build artifacts to a manifest job.
8. Compute sizes and SHA-256 hashes.
9. Generate canonical `update-manifest.json`.
10. Sign it with the protected Ed25519 release key.
11. Verify the signature using the same public key embedded in CtrlSpeak.
12. Create a draft GitHub Release and attach all five assets using their final
    names.
13. Download or inspect the uploaded assets from the draft release and audit
    their actual contents, runtime version, product identity, executable mode,
    signatures, checksums, and packaged dependency/runtime expectations.
14. Verify every URL in the final signed manifest resolves to the matching
    immutable draft-release asset without a cross-owner/repository/tag change.
15. Mark the release stable only after the complete audit matrix passes.

The workflow must not publish partial releases. If any platform build, test,
manifest generation, or signature verification fails, no installable stable
release is created.

Release builds start from a clean environment and do not restore PyInstaller or
native-library caches whose provenance cannot be tied to the tagged source.
Normal CI may use dependency caches, but a shipped artifact must not silently
link or package a stale native component. Release jobs record runner image,
Python, PyInstaller, and resolved dependency versions in the build provenance.

## 14. Settings and migration

Add only low-risk user preferences initially:

```json
{
  "settings_schema_version": 1,
  "update_channel": "stable",
  "last_update_check_at": null,
  "show_whats_new_on_update": true,
  "whats_new_last_seen_version": "0.5.0"
}
```

Repository identity, signing key, product, platform, and variant are not
user-editable settings.

Introduce a settings schema version before any migration is necessary. Update
migrations must be:

- explicit and sequential;
- idempotent;
- covered by old-to-new tests;
- backed up before write;
- atomic; and
- compatible with rollback where possible.

Loading settings must be resilient at field granularity:

- merge missing fields from typed/default settings;
- if one stored value is malformed, retain every independently valid field and
  fall back only for the invalid field;
- log the invalid field name and finite error category, never its value, because
  settings can contain API credentials;
- preserve a pre-migration backup until the new version passes its update health
  check;
- write the migrated file atomically with the existing user-only permission
  policy; and
- prove through tests that an invalid cosmetic/update preference cannot reset
  backend URL, token, model, device, mode, or correction data.

The v0.5.0 migration should preserve all v0.4 values, including API backend,
API URL/token, model, CUDA preference, audio device, discovery port, and mode.

After a verified update, the new healthy process may show the signed release
summary once when `show_whats_new_on_update` is true and the running version is
newer than `whats_new_last_seen_version`. A fresh v0.5.0 install stamps its own
version as already seen. Displayed notes are treated as untrusted text: use a
bounded plain-text subset, do not render arbitrary HTML, and open links only
through the existing trusted GitHub Release URL.

## 15. Logging and diagnostics

Use `%APPDATA%\CtrlSpeak\logs` or the Linux logs root for:

- `ctrlspeak.log` normal update UI/activity messages;
- `update.log` updater transaction messages; and
- a small redacted transaction summary suitable for support.

Log:

- current/target versions;
- release tag and manifest hash;
- selected platform/architecture/variant;
- download bytes and final artifact hash;
- state transitions;
- executable paths after normalization;
- replacement retries;
- health result; and
- rollback result.

Use finite internal error codes and sanitize URLs before logging them. Query
strings, fragments, embedded credentials, bearer tokens, cookies, and raw HTTP
error bodies must not re-enter logs through exception formatting. Secret-bearing
settings containers must redact their values in `repr`/debug output as a second
line of defense; this redaction does not substitute for secure file permissions.

Never log:

- transcription API bearer tokens;
- GitHub credentials;
- arbitrary clipboard/transcript contents;
- private signing keys;
- complete environment dumps; or
- response headers containing authorization/cookies.

## 16. Test plan

### 16.1 Pure unit tests

- semantic version equality, upgrade, downgrade, and malformed values;
- stable versus prerelease handling;
- platform/architecture normalization;
- exact product/channel/variant matching;
- zero, one, and multiple matching assets;
- manifest schema validation;
- valid and invalid Ed25519 signatures;
- wrong size/hash;
- minimum-updater-version enforcement;
- GitHub 200, 403/rate-limit, 404, 500, invalid JSON, timeout, and TLS errors;
- source-checkout install refusal;
- redacted logging; and
- transaction-path containment.
- update-coordinator generation changes and stale-callback rejection;
- runtime-mode classification; and
- settings migration, per-field salvage, secret redaction, and rollback backup.

### 16.2 Download tests

- streamed success;
- missing/incorrect `Content-Length`;
- interruption and cancellation;
- cancellation followed by a valid resume;
- stale partial refusal after a manifest/version/URL/hash change;
- already-complete partial verification before a request;
- `206` with correct and incorrect `Content-Range` starts;
- `200` returned to a range request restarts instead of appending;
- `416` with and without trusted size/hash evidence;
- connection/header/chunk stall timeouts;
- server-advertised and actually transmitted oversize bodies;
- excessive size;
- disk-full/write failure;
- stale partial cleanup; and
- candidate re-verification after copying to the install directory.

### 16.3 Replacement/rollback tests

- normal atomic replacement;
- temporarily locked executable and retry;
- unwritable installation directory;
- backup creation/hash failure;
- new process launch failure;
- missing, stale, or mismatched health marker;
- early new-process exit;
- successful health handshake;
- automatic rollback and old-version relaunch;
- interrupted transaction recovery; and
- strict refusal to touch paths outside the updater transaction/install target.

Use harmless dummy executables/scripts and temporary directories for these
tests. Core tests must never replace the actual running CtrlSpeak executable.

### 16.4 GUI tests

- state-driven button enablement;
- background worker responsiveness;
- progress events marshalled to the Tk thread;
- duplicate-click prevention;
- stale worker event rejection after retry/cancel;
- confirmation defaults to cancel;
- release-link behavior;
- checking/download/verification failures always produce a visible recovery
  action;
- one-time **What's new** behavior and plain-text sanitization;
- packaged versus source-mode messaging; and
- update blocked during active recording/transcription.

### 16.5 Release acceptance

On clean Windows and Ubuntu/X11 machines:

1. Install v0.5.0 with the stable filename.
2. Publish a controlled v0.5.1 test release.
3. Check, download, approve, restart, and confirm version/settings/models.
4. Repeat with remote API and bundled transcription modes.
5. Simulate a broken v0.5.2 candidate and verify rollback.
6. Test no-network and GitHub-rate-limit messages.
7. Confirm Windows Defender/antivirus behavior and handle-release timing.
8. Confirm Linux executable mode and X11 control center/tray behavior.
9. Confirm a standard build cannot select a Watcher asset.
10. Interrupt a large download, resume it, and confirm the final candidate is
    byte-for-byte identical to the signed artifact.
11. Corrupt one settings field before updating and confirm all other settings
    survive while only that field falls back safely.
12. Confirm the successful-update summary appears once and a rollback shows the
    rollback notice instead of claiming installation success.

## 19. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Compromised or malformed download | Signed manifest plus exact SHA-256 and size verification |
| Wrong product or OS installed | Exact product, variant, platform, and architecture matching |
| App cannot overwrite itself | Detached copied updater waits for full PyInstaller shutdown |
| Power loss during swap | Verified sibling candidate, retained backup, atomic replacement, transaction journal |
| New release cannot start | Health handshake and automatic rollback |
| Install path needs admin rights | Early write probe and manual-install guidance; no silent elevation |
| GitHub offline/rate-limited | Clear non-destructive error and retry later |
| Partial GitHub Release | Publish only after all platform/test/signature jobs succeed |
| Source work overwritten | Packaged-only installer; source mode is informational |
| v0.4 versioned filename becomes misleading | One-time v0.5 install under stable filename |
| Watcher accidentally replaces standard app | Separate product/variant trust identity and exact matching |
| Settings incompatible after rollback | Schema-versioned, idempotent migrations and pre-migration backup |
| Large 200+ MB downloads | Visible streaming progress, cancellation, full-download scope stated clearly |
| Interrupted download restarts from zero or appends corrupt bytes | Manifest-bound partials and strict HTTP Range/Content-Range validation |
| Network stalls forever | Finite connect/header/chunk stall timeouts and cancellable workers |
| Late worker result overwrites a newer check | Coordinator generation IDs and stale-event rejection |
| One malformed setting resets credentials/configuration | Per-field salvage, typed defaults, atomic migration, and pre-migration backup |
| Updater failure is visible only in logs | User-facing finite error categories and recovery actions |
| Release contains stale cached native code | Clean release builds plus package/provenance audit before draft publication |

## 20. Decisions required before implementation

The recommended defaults are listed first.

1. **Standard CtrlSpeak only for v0.5** (recommended), or include a separately
   designed Watcher channel now.
2. **Manual update checks only** (recommended), or opt-in automatic startup
   checks in the initial release.
3. **Ed25519 signed manifest required** (recommended), or checksum-only initial
   release with lower supply-chain assurance.
4. **Stable portable filename in a user-writable folder** (recommended), or an
   installed Program Files layout requiring an installer/elevation design.
5. **Windows x86-64 and Linux x86-64** (recommended), or additional
   architectures.
6. Whether to purchase/configure a Windows Authenticode certificate for v0.5.0
   or add it in a subsequent patch.

## 21. Definition of done

CtrlSpeak v0.5 self-update is complete only when:

- the v0.5 branch and tag history are clear and synchronized with GitHub;
- the control center can check stable releases without blocking;
- a compatible asset is selected exactly;
- the manifest signature, size, and SHA-256 are verified before shutdown;
- Windows and Linux packaged applications can apply an update and reopen;
- settings, credentials, models, CUDA assets, and correction data survive;
- a failed new version automatically restores the prior executable;
- source checkouts cannot be overwritten by the updater;
- GitHub Actions builds and publishes complete releases from tags;
- tests cover success, corruption, interruption, and rollback;
- interrupted downloads safely resume and stale partials cannot cross releases;
- stale background callbacks cannot corrupt current UI/update state;
- a malformed individual setting cannot reset unrelated valid settings;
- successful updates show sanitized release information once, while rollbacks
  report restoration accurately;
- release and recovery documentation is usable by another maintainer; and
- v0.5.0 has successfully updated itself to a controlled v0.5.1 release on
  physical Windows and Ubuntu/X11 machines.

## 22. Bootstrap expectation

An already deployed v0.4 executable has no updater code and therefore cannot
discover or install v0.5 by itself. Users perform one final manual replacement
to v0.5.0 under the stable installed filename. Starting with v0.5.0, normal
v0.5.1 and later upgrades use **Check for updates** in the CtrlSpeak control
center.
