## Microphone display

The default numeric readout is `0 / 100` through `100 / 100`. The saved checkbox
**Capture → Capture feedback → Show technical mic level (RMS dBFS)** restores
the technical readout. It applies live to the Hold recording capsule (normal
and compact layouts), Capture/Routing meters and tray flyout. Muted/paused
labels retain priority. Hands-free/Live retain their existing status layout.

The friendly value is the existing meter position rounded to a whole number:
`100 × clamp((dBFS + 60) / 60, 0, 1)`. Thus −60 or quieter → 0, −30 → 50,
−18 → 70 and 0 → 100. This is **not** percent amplitude, calibrated room SPL,
input gain or an audio-volume control. RMS measurement, smoothing, waveform,
recording, VAD thresholds and transcription/provider requests are unchanged.

`microphone_level_dbfs` defaults to false, accepts only booleans and is additive
to the existing settings schema. Existing/invalid/missing preferences safely
default to 0–100. Both choices survive save/reload. A save failure restores the
previous value/checkbox and shows an error. Internal `UiSnapshot.level_label`
remains technical for compatibility/diagnostics; visible UI uses one shared,
current-settings formatter instead. No new setting or credential is sent to an API.

## Intermittent Control shortcut investigation

Read-only inspection found the desktop running 0.8.3. Recent successful GPU
transcriptions and insertion outcomes were present. Existing logs do **not**
record individual hotkey decisions, so they cannot prove the exact cause of
every reported missed hold. No transcript or credential content was printed.

A concrete desktop defect was reproduced before changing the code:

1. Windows pynput's `KeyTranslator.__call__` uses the current modifier state
   for each key event and includes the stable Windows virtual-key code.
2. The old controller tracked translated character strings for all keys.
   Ctrl+C can press as `\u0003`, then release as `c` if Ctrl is released first;
   shifted punctuation (`!` / `1`) and layout changes can differ similarly.
3. The recognizer retained the unmatched press as a phantom held key. The next
   Right Ctrl then appeared to be a chord, failed the isolated-key requirement,
   and did not start recording. Three regression cases failed against 0.8.3.
4. `gesture_key_name` now uses stable Windows VK identities for gesture tracking,
   preserving semantic identifiers for Ctrl/F8/F9/F10/Esc. Original translated
   key objects still reach feedback/edit observation. X11 naming is unchanged.
   The previously failing cases now pass through the real controller and Hold
   pipeline, not a simplified mock recognizer.

The existing synthetic/injected-event filter is unchanged. Editing chords still
invalidate activation; a held physical editing key must still block a recording
shortcut. No timeout forcibly clears legitimately held keys, and no late audio
capture is started automatically.

A separate legitimate refusal is a previous request/microphone cleanup still
being active. When a committed hold cannot start, issue a rate-limited notice
and safe `busy`/`not_ready` log category rather than remaining silent. Release
and retry when ready. Ordinary short taps/double taps do not produce this notice.
The new logs contain no typed characters, raw key values or transcript text.
