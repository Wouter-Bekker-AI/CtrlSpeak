# CtrlSpeak 0.8.0 — optional hands-free and live dictation

## Scope and release status

0.8.0 adds desktop capture modes on the separate
`codex/dictation-modes-v0.8.0` development branch. Hold to Talk remains the
default workflow; Live requires an explicit opt-in. Existing provider routing,
caller-owned credentials, lossless transport, corrections, language constraints
and optional worker-GPU S1 cleanup remain in place.

Published on 2026-10-29 from source revision
`f3ae2de86e4566058f449a2ca07466d79bc692eb`. Automated build/deployment evidence is
recorded below. Interactive Windows/AnyDesk acceptance remains a user trial;
the Windows desktop was deliberately left on 0.7.7 for Check for updates.

## Modes and default gestures

| Mode | Start while idle | Finish | Transcript delivery |
| --- | --- | --- | --- |
| Hold to Talk | Hold Right Ctrl | Release Right Ctrl | One completed result |
| Hands-free Dictation | Double-tap Right Ctrl | Isolated Right Ctrl tap | One result after finishing |
| Live Dictation | Left Ctrl + Right Ctrl; release both | Isolated Right Ctrl tap | Completed phrases while recording continues |

In Hands-free and Live, an **isolated Left Ctrl tap** toggles mute/resume.
Escape or the explicit Cancel action cancels active work. Finishing and
cancelling are distinct: Finish processes recorded speech, while Cancel stops
capture and discards unsent queued audio. Neither undoes already-inserted text
or retracts a request that a provider has accepted. Already-held text remains
available for deliberate Copy/Discard.

An ordinary Ctrl+C/Ctrl+V-style chord is not an isolated tap and must not finish
or toggle mute. Hardware repeat is not a second tap. Short idle Right Ctrl
taps may start provisional microphone pre-roll for responsiveness, but an
uncommitted first tap is discarded without submitting an empty request.
If an editing chord interrupts a held recording, that capture is cancelled
rather than accidentally submitted.

Default recognition uses a 180 ms hold threshold, a 300 ms interval for the
second tap, and a 350 ms maximum isolated tap. These timings are internal
defaults, not new user-facing tuning sliders.

### Key customization and mouse-launched starts

Capture allows distinct primary and secondary keys selected from **Right Ctrl,
Left Ctrl, F8, F9 and F10**. Primary means hold/double-tap/finish; secondary means
mute/resume; their combination starts Live. Apply changes while idle. Saved
assignments and visible shortcut hints update together. Global hooks observe
input without suppressing it, so an application can still react to these keys;
use a less-conflicting assignment if necessary.

The Capture page, quick panel and tray expose start, mute/resume, finish,
cancel, Copy pending and Discard pending actions. Starting from a UI surface
gives a **three-second focus delay**: close the panel, focus a harmless intended
destination, then speak when the recording indicator appears. The keyboard
gestures do not impose that three-second UI delay.

## Platform and Live opt-in

Hold to Talk and Hands-free retain supported Windows and Linux **X11/Xorg**
operation. Native Wayland/headless global capture/injection is not supported.
Live Dictation in 0.8.0 is **Windows-only**. Its safety contract requires
reliable discrimination of physical keyboard input from CtrlSpeak's own
injection and a working mouse observer; it does not claim that capability on
Linux. An unavailable observer or unsupported platform prevents Live startup.

Enable Live in Capture only after acknowledging the warning. It is phrase
dictation, **not token streaming**, an OpenAI Realtime session, or continuous
partial-text replacement. Stable chunks are normally emitted after **650 ms of
silence**, and continuous speech is split at a maximum **eight seconds** per
chunk. Energy-based segmentation is not speaker recognition: background speech
can be captured too. The microphone controls remain essential.

The request path still includes encoding, upload, provider inference, optional
S1 cleanup, response and insertion. Actual latency depends on all of those,
not only the silence threshold. Each phrase is a separate normal request and a
paid route can incur usage for each one. Failures are not automatically retried.
There is no guaranteed latency or lower-cost promise.

## Mute, editing and safe delivery

- **Mute is a CtrlSpeak capture/delivery gate, not an operating-system hardware
  mute.** New microphone frames are discarded, not retained to replay after
  resume. A frame crossing a mute transition is discarded. The capture loop
  closes its input stream on mute and reopens it with fresh buffers on resume;
  an already-blocked native read must first return. Other applications'
  microphone access is unaffected.
- Work sent before mute may still finish. Its result is held instead of typed
  while muted. Finishing while muted does not secretly unmute or insert text;
  previously recorded speech can complete into held results.
- The persistent capsule names the active mode. A crossed microphone, **MUTED**
  text and frozen meter make mute explicit. Editing pause, finishing, pending
  results and actionable error reasons have distinct labels. During a normal
  Live request the microphone stays live, with a listening waveform and
  **Processing phrase** detail rather than a false stopped-recording claim.
- Physical keyboard/mouse activity in Live pauses capture and insertion.
  Capture may resume after keys are released and 600 ms of editing quiet;
  already-in-flight results keep their old delivery epoch and are held rather
  than inserted into the newly edited position.
- An unknown or changed foreground target pauses/aborts as appropriate. A Live
  target change requires explicit resume after focusing the intended field.
  A window identity is not proof of a particular text field or cursor. AnyDesk
  and similar viewers conceal remote field changes, so manually mute before
  remote navigation or editing when in doubt.
- Held text blocks automatic delivery and resumption until explicitly handled.
  **Copy pending** verifies the clipboard before clearing the copied queue;
  **Discard pending** clears it without inserting anything. Neither action
  automatically types or pastes into the active field. New pending results can
  still arrive from earlier requests; inspect the count before resuming.
- Partial or uncertain insertion is prominently reported. **Inspect existing
  text before copying/pasting pending output**, since a prefix might already
  have arrived. There is no automatic replay of the full result.

Live never deletes or rewrites committed text, moves the caret back, or
reconciles old paragraphs. Each accepted phrase goes to the currently armed
destination once. This intentionally trades seamless late rewrites for safe
editing and terminal/remote-desktop behavior.

## Formatting and corrections

Live always flattens generated line breaks, tabs and unsafe controls through
the desktop sanitization policy, even if S1 paragraph formatting is enabled.
The insertion adapter adds a trusted ordinary space after a nonempty Live
phrase so adjacent phrases do not run together. It never adds an Enter to
submit a terminal command or message.

Hold and Hands-free retain the saved **Preserve paragraphs and line breaks**
preference when eligible S1 cleanup was actually applied. The gateway and worker
do not flatten the API response, and Nova/Telegram can retain formatted text.
Disabling Live or rolling back does not change the existing S1 preference.

Per-phrase Live output is not tracked as a whole field for automatic Enter
correction feedback. Use explicit **Submit correction…** for known-word rules;
the API's correction and feedback endpoints are unchanged. Hold/Hands-free
retain the existing whole-field feedback policy where enabled.

## Resource bounds, ownership and privacy

| Resource | Current bound/behavior |
| --- | --- |
| Continuous session | 30 minutes; capture pauses at the limit |
| Hands-free audio buffer | 100 MiB; capture pauses at the limit |
| Live pending request queue | Three waiting phrases, plus at most one executing request |
| Held text | 128,000 characters; exceeding it truncates with an explicit warning and ends capture |
| Concurrent microphone ownership | One; a replacement cannot start until the prior owner actually exits |
| Editing quiet interval | 600 ms after physical editing, with keys released |

When the Live queue fills, capture pauses instead of buffering indefinitely.
Already-accepted phrases can finish into held text; copy/discard them and resume
explicitly. A transcription failure pauses the session and clears later queued
phrases rather than delivering text across a missing phrase. A stuck native
microphone remains owned and blocks another recording; a timeout must not
pretend that native ownership has vanished.

Audio and pending text are session data, not a new persistent history feature.
Temporary recordings use the managed cleanup path. The existing bounded
memory-only failed-recording recovery may retain one retryable failed clip;
an explicit retry can incur another charge. Existing protected gateway audits
and bounded local insertion audits still contain private transcript data under
the 0.7.6 policy. UI status/error labels use fixed safe messages, not raw
transcripts, exceptions or credentials. Mute/cancel do not promise forensic
erasure of Python/OS buffers, paging or provider-side copies already sent.

## Return to 0.7.7

For a writable packaged 0.8.0 installation:

1. Finish/cancel recording and handle any pending text first.
2. Open **Updates → Roll back to 0.7.7** and confirm the lookup.
3. The updater selects only the pinned signed stable `v0.7.7` release; inspect
   the target, download it, then explicitly choose restart/install.
4. Verify the running version is 0.7.7 and check an ordinary Hold to Talk
   recording. The new modes are no longer available.

Rollback uses the normal signature, product/platform/architecture, hash/size,
atomic replacement and startup-health checks; it is not an unsigned overwrite
or a general arbitrary downgrade. Existing settings, saved native-vault
credentials, models and corrections remain. A new normal Check for updates
clears rollback intent and can discover 0.8.0 again. Source checkouts use Git,
not executable self-replacement.

Desktop rollback does **not** roll the gateway or worker back. The unchanged
API supports 0.7.7 clients against the 0.8.0 fleet. Operational server rollback
uses preserved release selectors; never restore an older database over newly
submitted corrections merely to change application code.

## Coordinated deployment and Nova

Use the existing signed release transaction: run serialized verification,
build packages, verify signed draft assets, stage mandatory targets, preserve
rollback selectors/database, activate services, verify health/version/revision
and synthetic canaries, then publish the desktop update.

- Gateway and Ubuntu GPU worker use the same signed source revision. Preserve
  tokens, model settings, provider order, correction database and private VPN
  access. Activation can restart the CtrlSpeak services; do not confuse this
  with restarting Nova's Hermes Gateway.
- Update Nova's external command helper as part of the transaction. It remains
  outside Hermes source and needs **no Hermes restart**. Existing Telegram
  voice-note handling and selected cleaned/ordinary transcript semantics do
  not change, and no desktop Live gestures apply to Nova.
- Keep the Windows desktop running until its user chooses **Check for updates**
  and installs. The laptop can do the same when online. Do not force an active
  desktop upgrade as part of backend activation.
- Check the installed Ubuntu desktop companion separately from its worker
  service where it is managed by the fleet deployment; Linux still exposes
  Hold/Hands-free, not Live.

No new public endpoint, exposed port, secret distribution scheme, server model
download or Hermes core patch is required by these desktop modes.
