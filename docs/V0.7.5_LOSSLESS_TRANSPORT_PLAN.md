# CtrlSpeak 0.7.5: lossless audio transport and coordinated releases

Status: implementation-ready design, investigated on 18 September 2026.
No application code, production configuration, releases or services were changed
by this investigation. This document records the agreed direction and the
implementation/deployment acceptance criteria; it is not a deployment receipt.

## 1. Required outcome

- Windows desktop and laptop compress captured audio before uploading it.
- Nova uses the same transport preparation policy through an external command
  helper, without adding patches to Hermes core or installing dependencies in
  Hermes's own environment.
- The gateway receives compressed audio and keeps it compressed when forwarding
  to the home Ubuntu GPU worker. The worker decodes it for transcription.
- OpenAI receives the compressed file directly when its API supports it. Any
  necessary compatibility conversion belongs at the gateway and must not add
  lossy encoding, downsampling, silence trimming or other audio alteration.
- Return text normally; text compression is not the objective.
- One Git commit/tag identifies the desktop, gateway, worker and Nova helper.
  Backend deployment is automated and verified before the desktop release is
  offered through Check for updates. No independent blind `git pull` timers.
- Preserve provider preferences, fast failover, saved keys, identities, known-word
  corrections, exact overrides, optional GPU S1 cleanup and response selection.

### Nova's actual input and extension point

The configured STT command is:

```text
/home/ubuntu/services/whisper-transcription/scripts/hermes-stt-api {input_path} {language} {output_path}
```

The live Hermes command-provider path passes ordinary Ogg/WAV inputs to that
command without converting them to WAV or applying its built-in cloud-provider
AAC/silence-trimming path. Special upstream preprocessing exists for other
formats such as SILK/CAF; this patch does not redesign those unrelated paths.

The three newest files in the profile's audio caches were inspected with ffprobe
for metadata only: all were mono Ogg/Opus at a reported 48 kHz. Examples:

- 75.85 seconds: 277,309 bytes.
- 4.07 seconds: 13,524 bytes.
- 91.65 seconds: 332,194 bytes.

No audio was played, retranscribed, sent to a provider or copied out for this
inspection. These are cached-file observations, not a guarantee about every
future attachment.

The helper currently uploads the input file unchanged. Its companion
`ctrlspeak-response-adapter.py` preserves the one-transcript/feedback-sidecar
contract. Live copies differ from the saved Nova handover copies only by an
extra trailing blank line in the snapshots. The response adapter is not yet
tracked in this CtrlSpeak repository; reconcile it into versioned source during
implementation instead of overwriting the live integration with the older
repository wrapper.

FFmpeg/ffprobe are installed on Nova. PyAV is not installed in Hermes's virtual
environment, and should not be installed there for this change. A dedicated
CtrlSpeak helper environment keeps transport dependencies outside Hermes.

### Compression evidence

The desktop currently captures PCM16, 44.1 kHz, mono WAV: 88,200 audio bytes per
second, approximately 5.29 MB per minute, excluding container overhead.

An in-memory PyAV FLAC benchmark of the bundled 20-second test recording found:

| Setting | FLAC size | Reduction from 1,769,086-byte WAV | Median encode time |
|---|---:|---:|---:|
| Level 0 | 1,012,616 bytes | 42.76% | 23.26 ms |
| Level 5 | 972,431 bytes | 45.03% | 20.09 ms |
| Level 8 | 964,550 bytes | 45.48% | 34.60 ms |

Level 5 is the initial default. These are three-run measurements on this desktop,
not latency promises for all hardware. Level 5 decoding took about 13 ms.
Decoded PCM bytes and SHA-256 matched the source exactly, and faster-whisper's
preprocessed input arrays were identical. Synthetic and stereo fixtures also
passed. Full-range random noise grew approximately 2%, confirming that no fixed
compression saving can be guaranteed.

## 3. Final transport policy

Use one deterministic preparation component shared by the desktop and an external
Nova command-line adapter. No model/tool reasoning is involved in compression.

1. Inspect the actual audio/container, not just the extension.
2. For supported integer PCM recordings, encode lossless FLAC, preserving sample
   rate, channel count, sample precision and sample count. Initial guaranteed path
   is CtrlSpeak's PCM16 recording format; explicitly test any additional widths.
3. Pass valid FLAC through unchanged.
4. Pass already-compressed, downstream-supported Ogg/Opus and other supported
   formats through byte-for-byte. This adds no quality loss. Existing Opus is
   lossy at its original encoding stage; converting it to FLAC cannot restore
   that original information and can increase its size substantially.
5. Never silently quantize floating-point audio or reduce bit depth just to force
   FLAC. Unsupported lossless conversions, encoder failure, tiny files or cases
   where FLAC is larger retain the original supported input with an explicit
   diagnostic. These are compatibility exceptions, not new lossy encoding.
6. Use correct extension-bearing filenames and explicit MIME types (`audio/flac`
   for FLAC, `audio/ogg` for Ogg). Preserve the original recording until the
   request ends; remove only helper-owned temporary files on every exit path.

The normal Windows recording path therefore uses FLAC. Nova's present Telegram
path normally takes the already-compressed pass-through branch, while future
uncompressed attachments use FLAC. This meets the uniform *preparation policy*
without requiring every input to be converted to the same codec.

### Gateway and worker contract

- Retain the existing multipart API and response semantics. Accept legacy WAV.
- Advertise an additive transport protocol/capability field describing verified
  accepted formats, limits and build revision. Old clients ignore new fields;
  new clients can safely use the legacy path if capabilities are absent.
- Forward the original prepared file unchanged to the worker or OpenAI whenever
  supported. Keep it available throughout provider fallback; do not repeatedly
  encode/decode it or accidentally upload an exhausted stream.
- Decode at the selected inference endpoint. Keep local Tiny fallback functional.
- Preserve upload-size checks and add actual decoded-sample/memory/duration
  bounds, not merely trusted container duration. Calibrate these against the
  existing 100 MiB upload limit so compressed inputs cannot defeat resource
  controls. Malformed/truncated files fail promptly with bounded diagnostics.
- Record format, input/upload bytes, preparation time and compression outcome.
  Distinguish upload/request time from worker inference time; do not label total
  HTTP request time as pure upload time. Never log audio, transcripts or keys as
  transport diagnostics.
- No retries of an ambiguous completed provider request merely to change format;
  avoid duplicate transcription or billing. Unsupported-format conversion must
  be explicit and tested against the relevant provider response.

## 4. Nova integration boundary

Package the helper, compression library and response adapter as CtrlSpeak-owned
code from the same release commit. Use an isolated, minimal helper environment:
no Whisper/CUDA/model downloads and no Hermes Python-package changes.

Keep the configured command path as a thin compatibility launcher. It should
resolve one immutable helper release directory at invocation start and use that
same directory for encoding and response handling. Atomic activation then affects
new invocations without changing an in-flight request's companion code.

Preserve the current command arguments, protected credential locations, key
forwarding, GPU-preferred strategy, `cleanup=true`, language setting, output text
and schema-2 `.ctrlspeak.json` sidecar. Preserve bounded timeouts, process cleanup
and restricted temporary-file permissions. Add helper `--version` and a safe
self-test/health command. No new Hermes skill is required to remember to run it,
and normal helper updates should not require a Hermes service restart.

## 5. Coordinated GitHub deployment

### Existing gap

`.github/workflows/release.yml` currently builds Windows/Linux desktop binaries,
signs metadata, audits five public assets and publishes stable immediately.
There is no worker/gateway/helper deployment stage. Service tests are in a
separate branch/PR workflow and must become an explicit release dependency too.

Repository access with administration/push permission and the existing release
signing secret were verified without exposing credentials. GitHub has no
self-hosted runners, deployment environments or additional deployment secrets
configured. The local `gh` command has no standalone login; the existing Git
credential manager provides authenticated access. Do not print or persist that
credential into the repository.

### Automation design

Use the existing GitHub-hosted build runners, plus a protected deployment job
with a dedicated, narrowly restricted WireGuard peer. Connect through Nova's
existing `wg-fabric` hub (UDP 51820), not an assumed `wg0` interface. GitHub
documents this hosted-runner networking pattern; no extra VM or general-purpose
runner inside Hermes is needed.

One-time implementation bootstrap must:

- Reconcile the current WireGuard peer/address inventory and reserve an unused
  CI address; do not assume historical unused addresses are still free.
- Provision separate deployment credentials, pinned SSH host keys and restricted
  deploy commands for the three exact hosts. Do not reuse personal administrator
  keys as broad GitHub automation secrets.
- Restrict management connectivity and host authority to the release operation;
  keep SSH/model APIs private. Audit cloud security group, guest firewall and
  listeners independently. The runner must not gain general home-LAN access.
- Configure a protected release deployment environment/tag policy; never expose
  deployment/signing credentials to pull-request code or untrusted refs.
- Verify the exact tagged commit belongs to the approved release branch, enforce
  one active fleet deployment, use hard timeouts and always clean up tunnel and
  temporary credential files. Do not cancel a deployment mid-activation just
  because a second tag is pushed.

No existing Nova-to-worker/gateway SSH path should be assumed: bounded tests
from Nova did not establish access. Desktop administration of all three required
backend hosts works with their documented, host-specific keys. The CI route is
a bootstrap requirement, not something already installed.

### Release transaction

1. Commit and push reviewed code, tests, helper integration, docs and deploy
   automation. Create immutable `v0.7.5`; never deploy a moving branch HEAD.
2. Run desktop, server and helper tests against that exact commit. Build signed
   Windows/Linux binaries and independently audit their packaged codecs.
3. Produce signed deployment metadata/source release identity recording
   the common commit, role versions, compatible transport protocol, checksums
   and dependency provenance. Implementation uses an additive `deployment`
   section in the existing signed manifest and checks out the signed Git SHA;
   a second signature format/source archive is unnecessary. Keep the desktop schema and
   asset names readable by 0.7.4. Update five-assets-only release audit assumptions
   deliberately if backend release assets are added.
4. Create a draft release. Stage immutable source checkouts/helper environments
   on **all three required backend hosts before activating any**. Check disk,
   dependencies, credentials, current Git deltas and rollback readiness. Back up
   the gateway database/configuration consistently without resetting live data.
5. Drain bounded in-flight requests and activate worker first, gateway second,
   Nova helper third. Keep 0.7.4 request compatibility throughout. Each host uses
   an atomic release selection with its previous runtime retained for rollback.
6. Verify live versions/revisions, health, FLAC and Opus routing, GPU/OpenAI/Tiny
   fallback, corrections, cleanup and Nova's selected transcript/sidecar. Update
   the installed Ubuntu desktop companion from the signed Linux asset as part
   of host reconciliation; do not confuse its executable with the GPU service.
7. Only after required backend checks pass, publish stable/latest. Existing
   desktop clients then discover 0.7.5 through their current signed updater.
8. Wouter clicks Check for updates and Update on Windows; do not manually replace
   his desktop executable and bypass the updater acceptance test. Verify this
   upgrade and preserved preferences/key separately from backend deployment.

Each host writes a deployment receipt: target/actual version, commit, artifact
hash, protocol, timestamp, verification result and rollback release. Publish a
sanitized workflow summary, not private host details or credentials. The helper's
version is CtrlSpeak's release version, not Hermes's independent upstream version.

### Failure and offline-device policy

This is a coordinated rolling deployment, not a physically simultaneous update
across disconnected machines. Backend staging/activation failure keeps the
candidate unpublished and triggers bounded rollback of activated components.
If rollback itself is unreachable, report exact degraded/pending state; never
claim restored coherence without verification. Preserve successful user writes;
do not restore an old corrections database just to roll back application code.

The gateway, GPU worker and Nova helper are mandatory pre-publication targets.
An offline mandatory target pauses/fails the candidate deployment rather than
silently being skipped. Reconcile receipts before retrying the same release.

Windows clients remain user-installed. An offline laptop cannot be updated and
must be shown as pending, not fleet-complete. Old clients remain compatible with
the new backend until their next successful update; new clients handle an older
compatible endpoint safely. This temporary, visible version difference is
different from broken protocol compatibility. A disabled Ubuntu desktop GUI
need not be launched merely to install its verified update.

## 6. Required acceptance tests

- Bit-perfect PCM round trips: sample bytes/count, channels, rate and precision;
  silence, speech, noisy input, stereo, empty/truncated input and long input.
- Already-compressed pass-through: original uploaded bytes remain identical.
- Packaged Windows and Linux codec self-test, without microphone/UI/model loads.
- Sender preparation is off the UI thread; cancellation/timeouts clean up
  children and helper-owned files without deleting source audio.
- Gateway forwards the compressed bytes across both provider paths and retains
  files/stream position correctly during fallback. No compression/decompression
  loop, quality-changing conversion or uncontrolled decoded allocation.
- Real worker FLAC/Ogg canaries and minimal non-personal OpenAI format canaries
  during implementation acceptance; documentation support alone is not a claim
  that a live provider canary has already passed. No paid canaries ran during
  this investigation.
- Preserve known-word rules, exact overrides, GPU-only S1 behavior, response
  provenance and one canonical Nova input with its feedback sidecar.
- 0.7.4 desktop discovers and verifies the candidate metadata in an isolated
  test; old/new API combinations remain usable; after publication the normal
  GUI offers the release and installs it with rollback/settings retention.
- Deployment tests cover partial staging, unhealthy worker, gateway failure,
  helper failure, offline host, repeat invocation and failed publication after
  successful backend activation. Never republish different bytes under one tag.
- One test-suite process per host at a time, bounded subprocesses/waits, and
  cleanup/reaping on success, error or cancellation.

## 7. Implementation sequence and documentation

1. Shared transport preparation library and isolated Nova CLI; focused tests.
2. Desktop upload integration; gateway/worker capability, validation and telemetry.
3. Bring the live helper/response contract into Git without unrelated Hermes edits.
4. Signed deployment metadata, protected CI networking and transactional deployer.
5. Update README, API/service docs, updater/release runbook and Nova integration
   handoff with actual tested format behavior and coordinated rollout procedure.
6. Run acceptance, tag/build/stage/deploy/verify, publish stable, then validate the
   user-triggered Windows updater and record any offline clients explicitly.

There is no remaining audio-format or Hermes-extension design blocker. Private
CI deployment access still needs to be provisioned and tested as implementation
work. Recheck production source/state immediately before changes; today's live
inspection is a dated baseline, not permission to overwrite later edits.
